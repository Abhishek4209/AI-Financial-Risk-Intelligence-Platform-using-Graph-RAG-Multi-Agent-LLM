# Fresh production deployment

This repository is configured for a fresh Vercel frontend and Render API/PostgreSQL deployment. The existing services are not modified by the Render Blueprint because its first sync uses `create_new`.

## Architecture

- **Frontend:** Vercel, built from `frontend/` with Vite.
- **API:** Render Docker web service, built from the repository root.
- **Database:** Render PostgreSQL in Singapore, connected over Render's private network.
- **Optional services:** Redis and Neo4j are disabled unless their connection settings are supplied. The API readiness endpoint reports these as disabled rather than failing.
- **Release gate:** GitHub Actions deploys only after the `CI` workflow completes successfully on `main`.

## 1. Render setup

1. Open the Render Blueprint dashboard and connect this repository, branch `main`, file `render.yaml`.
2. The Blueprint is named **Ledgerline production stack**. Its first plan needs billing information in the Render workspace; no resources have been created yet.
3. Review the proposed web service and PostgreSQL resource, including current pricing, before approving the Blueprint sync.
4. Set `CORS_ALLOWED_ORIGINS` to the exact Vercel production origin, for example `https://your-project.vercel.app`.
5. Keep `DATABASE_URL` generated from the Blueprint's PostgreSQL resource. Do not paste a database password into GitHub or source control.
6. Keep `AUTH_DISABLED=false`. A strong `JWT_SECRET_KEY` is generated by Render.
7. Only configure `REDIS_URL`, `NEO4J_URI`, and `NEO4J_PASSWORD` if those managed services have actually been provisioned.
8. After the first service is created, open its Settings page and create a Deploy Hook. Save the URL as the GitHub Actions secret `RENDER_DEPLOY_HOOK`.

The API exposes `/health` for the platform health check and `/ready` for dependency readiness. PostgreSQL is required; Redis and Neo4j are optional.

## 2. Vercel setup

1. Create a new Vercel project from this repository.
2. Set **Root Directory** to `frontend`, framework preset to **Vite**, and production branch to `main`.
3. Set the production environment variable `VITE_API_URL` to the full Render API origin, such as `https://your-api-service.onrender.com` (no trailing slash).
4. Add the same value as the GitHub Actions secret `VITE_API_URL`.
5. Add the exact Vercel production origin to Render's `CORS_ALLOWED_ORIGINS`.
6. Obtain a Vercel access token, team/org ID and project ID for GitHub Actions.

The Vercel project configuration in `frontend/vercel.json` supports client-side React Router routes.

## 3. GitHub Actions secrets

Add these repository secrets under **Settings → Secrets and variables → Actions**:

| Secret | Value |
|---|---|
| `VERCEL_TOKEN` | Vercel access token |
| `VERCEL_ORG_ID` | Vercel team ID or personal account scope ID |
| `VERCEL_PROJECT_ID` | New Vercel project ID |
| `VITE_API_URL` | Public Render API base URL |
| `RENDER_DEPLOY_HOOK` | Deploy Hook URL from the new Render API service |

The existing `QLTY_COVERAGE_TOKEN`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, and `NOTIFICATION_EMAIL` secrets are not replaced.

## 4. Release flow

A push to `main` runs the existing CI checks. After the CI workflow succeeds, `.github/workflows/deploy.yml` deploys the frontend to Vercel and triggers the Render deploy hook. If a provider's required secrets are missing, that provider's deployment step is skipped and the workflow summary reports which configuration is missing.

## 5. First-deploy validation

After both providers finish:

- Open `https://YOUR-RENDER-SERVICE.onrender.com/health`; expect HTTP 200 and `status: ok`.
- Open `https://YOUR-RENDER-SERVICE.onrender.com/ready`; expect `status: ready` and PostgreSQL `ok`. Optional Redis/Neo4j may report `disabled`.
- Open the Vercel production URL and check the browser Network tab. API calls must target the Render URL, not localhost or the Vercel origin.
- Test overview, credit risk, fraud, documents, and compliance endpoints individually.
- Configure database schema/migrations and seed/demo data only after confirming the new database is the intended target. Do not run a seed or restore against any existing production database by accident.

## Resource sizing and data notes

The backend requirements include PyTorch, Transformers, Sentence Transformers, vector stores, OCR and multiple ML libraries. A small/free web instance may run out of memory or take a long time to build. Confirm the current Render plan limits and monitor the first build before treating the service as production-ready. The Blueprint intentionally does not provision Redis, Neo4j, a vector database, object storage, or external LLM credentials automatically.

Do not commit `.env`, model credentials, production customer data, or database dumps. The Docker build context excludes local `data/` and environment files; ensure any model files required for inference are versioned or stored in durable artifact storage.
